Finding

Manrope cannot render standard Uzbek oʻ and gʻ

The brief asked whether the display face handles the Uzbek modifier letters at hero size. It does not, and this is not cosmetic: the API already emits the character Manrope is missing, 657 times across the shot plans in out/pack. Rendered below in a real browser with the real webfont.

1 · Standard Uzbek Latin  —  U+02BB MODIFIER LETTER TURNED COMMA

Oʻzbekcha yoʻnalish, gʻoya

Kadrlar rejasi: mahsulot aniq koʻrinadi, yorugʻlik sirt boʻylab yuradi.

Broken. Manrope has no glyph at U+02BB. The browser silently substitutes a fallback face for that one character, so the mark above changes weight, width and colour mid-word. This is the codepoint the API already writes (657 times in the Uzbek shot plans, plus 14 of U+02BC).

2 · What the planning documents use  —  U+2018 LEFT SINGLE QUOTATION MARK

O‘zbekcha yo‘nalish, g‘oya

Kadrlar rejasi: mahsulot aniq ko‘rinadi, yorug‘lik sirt bo‘ylab yuradi.

Renders. Manrope has this glyph, which is why the artboards use it. But it is a quotation mark, not a letter: a browser may break a line after it, double-click word selection stops at it, and search for "oʻzbek" will not match "o‘zbek". It is the pragmatic choice, not the correct one.

3 · ASCII fallback  —  U+0027 APOSTROPHE

O'zbekcha yo'nalish, g'oya

Renders everywhere and is what sellers type on a phone keyboard. Reads as cheap at hero size, and carries the same non-letter problems as case 2. Useful only as input normalisation: accept it from the seller, store the canonical form.

The api repo and the planning docs already disagree with each other, and neither choice survives Manrope untouched. This needs one decision before any text ships, and it is a contract-level decision, not a styling one: it changes what the API stores and what the web app searches.
